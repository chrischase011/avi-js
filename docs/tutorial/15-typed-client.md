# 15. Typed client

> **Status: Runnable from 0.3.0.** Everything on this page works with Avi.js 0.3.0 or newer.

Your routes already know their paths, schemas and results. `avi client` turns that into one
`Api` type, and `@avijs/client` calls your API with it: paths autocomplete, a wrong body fails to
compile, responses are typed. It works the same for decorators and the explicit API.

```ts
import { createClient } from '@avijs/client';
import type { Api } from './api.gen.js';

const api = createClient<Api>({ baseUrl: 'http://localhost:3000' });

const user = await api.get('/users/:id', { params: { id: 1 } });
//    ^? { id: number; name: string }
await api.post('/users', { body: { name: 'Shiela' } });
await api.post('/users', { body: {} }); // compile error: name is missing
```

## Generate the Api type

Projects from `npm create avi` include `src/api.gen.ts` and a `client` script. Run it after you
add, remove or move a route:

```sh
npm run client   # avi client: writes src/api.gen.ts
```

```ts
// src/api.gen.ts, generated by avi client
import type { MethodEndpoint } from '@avijs/core';
import type { UsersController } from './modules/users/users.controller.js';

export interface Api {
  'GET /users': MethodEndpoint<'/users', UsersController['findAll']>;
  'POST /users': MethodEndpoint<'/users', UsersController['create']>;
  'GET /users/:id': MethodEndpoint<'/users/:id', UsersController['findOne']>;
}
```

The file points at your controllers instead of copying their types, so it stays exact and only
changes when routes do: change a DTO or a handler and the client follows on the next compile.

`avi client` finds the app from `AviFactory.create(...)` or `app.register(...)`. Pass
`--root src/app.module.ts#AppModule` if it cannot, and `--out` to write elsewhere. In CI,
`avi client --check` fails when the file is out of date.

## Where the types come from

| Part     | From                                                                    |
| -------- | ----------------------------------------------------------------------- |
| `params` | The `params` schema's input, else the path: `/users/:id` takes `{ id }` |
| `query`  | The `query` schema's input; any query when there is no schema           |
| `body`   | The `body` schema's input; any body when there is no schema             |
| Response | The `response` schema's output, else what the handler returns, as JSON  |

Request types are what the schema **accepts**, before transforms: a query schema that turns `'2'`
into `2` takes strings from the client. Responses are what JSON makes of the result: a `Date`
arrives as a `string`, `undefined` fields are optional, `reply(body, { status })` gives `body`'s
type. Streams and `sse()` return the `Response`.

For decorators, the schema reaches the client through `RouteContext`:

```ts
@Post('/', { schema: create })
create(ctx: RouteContext<typeof create>) { ... } // the client sees create.body
```

With `ctx: Context`, the route still gets a typed response, but not a typed body; `avi client`
warns about it (AVI105).

## What avi client cannot see

It reads your code without running it, so it needs routes it can follow: string literal paths
and prefixes, controllers in exported consts or classes, and route lists written as arrays.
Anything else is left out with a warning that says how to fix it:

| Code   | Means                                                                    |
| ------ | ------------------------------------------------------------------------ |
| AVI101 | No app found: pass `--root`                                              |
| AVI102 | A controller is not exported, or is written inline: export it as a const |
| AVI103 | A path, prefix or route list is computed: use literals                   |
| AVI104 | A module cannot be read statically                                       |
| AVI105 | A decorator route has a schema, but `ctx` is not a `RouteContext`        |

## Calling the API

```ts
const api = createClient<Api>({
  baseUrl: 'https://api.example.com',
  headers: () => ({ authorization: `Bearer ${getToken()}` }), // runs per request
  init: { credentials: 'include' }, // more fetch options for every request
});

await api.get('/tasks', { query: { status: 'doing' }, signal: AbortSignal.timeout(5000) });
```

Every method (`get`, `post`, `put`, `patch`, `delete`, `head`, `options`) takes the route's path
as written on the server and an options object with `params`, `query`, `body`, `headers` and
`signal`. Objects are sent as JSON; `FormData`, strings and bytes as they are.

Path parameters are percent-encoded, so a value cannot add segments to the path. Values that
would change the route throw a `TypeError` instead of being sent: `.` and `..` (URLs resolve them,
so `/users/../posts` would call `/posts`), and an empty value (`/users/` is the route `/users`, so
deleting user `""` would hit the collection). `baseUrl` cannot have a query or a fragment.

A status outside 2xx throws an `AviClientError`:

```ts
import { AviClientError } from '@avijs/client';

try {
  await api.get('/users/:id', { params: { id: 404 } });
} catch (error) {
  if (error instanceof AviClientError) {
    error.status; // 404
    error.body; // { statusCode: 404, error: 'Not Found', message: 'User not found' }
    error.requestId; // matches the server's logs
  }
}
```

`api.raw.get(...)` returns the `Response` untouched and never throws for a status.

`@avijs/client` has no dependencies and runs anywhere `fetch` does: browsers, Node.js, Bun, Deno
and workers.

## Typed tests

Pass the same `Api` to the test client and use `client.api`:

```ts
const client = await createTestClient<Api>(AppModule);

const res = await client.api.get('/users');
assert.ok(res.ok);
assert.equal(res.body[0]?.name, 'Shiela'); // res.body is typed once ok is checked
```

`client.api` never throws for a status, so tests can check errors the same way. The untyped
`client.get('/users/1')` calls still work alongside it.

## A frontend in another repository

The generated file imports your server's code, so it suits a monorepo, where the frontend can
import from the server package. For a frontend in its own repository, generate types from your
[OpenAPI document](11-openapi.md) instead, for example with `openapi-typescript`.
